# 작업 흐름

**협업 규칙 초안**

적용 범위는 [협업 규칙 안내](../../CONTRIBUTING.md) 참고.

## 1. Issue로 할 일 공유

Issue는 해결할 작업이나 질문 단위.

하루에 못 끝내도 같은 Issue에서 계속 진행.

| 템플릿 | 용도 | 라벨 |
|---|---|---|
| 기능·작업 | 기능 구현, 문서 작성, 설정·정리 | 기능은 `enhancement`, 문서는 `documentation`, 설정은 생략 가능 |
| 버그 | 발견한 오류 | `bug` |
| 논의 | 아직 결정하지 못한 질문 | `question` |

### 작성

- 구현 작업은 **담당자 한 명** 지정
- 목표·**완료 조건** 공유
- 작은 수정이나 기능에 딸린 문서 변경은 별도 Issue 없이 PR에 포함 가능
- 버그는 원인을 몰라도 현상·재현 방법 작성
- 재현하지 못했다면 그 사실과 관찰 조건 기록

### 진행·범위 변경

- **완료 조건** 충족 여부를 확인·검증한 뒤 체크
- 작업 중 알게 된 내용에 맞춰 범위 조정 가능
- 범위가 크게 달라지면 상대방과 공유하고 댓글에 변경 이유 기록
- 작업이 너무 크면 남은 범위를 새 Issue로 분리하고 연결
- 설명 없이 미완료 항목을 지워 완료 처리 금지
- 논의는 댓글로 진행

예: `지출 등록·목록·수정·삭제` 중 등록만 완료했다면 기존 Issue를 등록 범위로 조정하고 남은 작업은 새 Issue로 연결.

아직 따로 완료한 결과가 없다면 기존 Issue 유지.

### 종료

- 기능·작업·버그는 **완료 조건과 검증 근거** 확인 후 종료
- 관련 PR이 있으면 merge 확인
- 파일 변경 없는 설정·조사 작업은 근거를 Issue에 기록
- 논의는 결론·이유를 기록하고 관련 문서나 작업 Issue에 반영 후 종료

## 2. 브랜치와 작업 범위

- 기본 브랜치는 **`main`**
- 초기 저장소 구성 이후 `main` 직접 작업·push 금지
- 최신 `main`에서 작업 브랜치 생성
- 따로 검증하고 합칠 수 있는 작업 하나당 PR 하나
- 같은 기능에 필요한 UI·API·DB 변경은 같은 PR에 포함 가능
- 작업 시작 전 맡을 범위와 겹치는 파일 공유
- DB 구조·공통 설정은 변경 방향 사전 합의
- 선행 작업이 필요하면 선행 PR merge 후 최신 `main`에서 시작
- 최신 `main` 반영: `git fetch origin` 후 `git merge origin/main` 실행
- 충돌 해결 후 관련 검증 재실행

| 종류 | 브랜치 예시 | PR 제목 예시 |
|---|---|---|
| 기능 | `feat/add-expense` | `feat: 지출 등록 구현` |
| 버그 | `fix/month-filter` | `fix: 월별 지출 조회 오류 수정` |
| 리팩터링 | `refactor/expense-validation` | `refactor: 지출 검증 로직 정리` |
| 설정·정리 | `chore/setup` | `chore: 개발 환경 설정` |
| 문서 | `docs/readme` | `docs: 로컬 실행 방법 추가` |

브랜치 이름: `feat/add-expense`처럼 종류 뒤에 짧은 영어 이름 사용.

단어는 소문자와 하이픈으로 연결.

리팩터링: 기능 동작을 유지하면서 코드 구조 개선.

독립적인 정리는 별도 PR로 진행하고, 기능 구현에 필요한 작은 정리는 해당 PR에 포함 가능.

## 3. Commit

- 복구하고 확인하기 좋은 시점마다 commit
- `feat: 지출 등록 구현` 형식 권장, 중간 commit 형식은 자유
- commit할 변경 내용을 확인하고 **이번 작업의 파일만** 포함
- 다른 작업자의 변경은 임의 수정 금지
- **Secret**·개인 환경 파일·불필요한 생성 결과물 commit 금지
- 로그·스크린샷에서도 민감한 정보 제외
- 공유한 commit 이력은 `rebase`, `amend`, force push로 변경 금지

## 4. PR과 검증

### 작성

- 구현·검증 후 PR 템플릿 작성, 상대방에게 리뷰 요청
- 진행 중 피드백이 필요하면 **Draft PR** 사용
- PR 제목은 표의 예시처럼 종류와 변경 내용 작성
- Squash merge 후 commit 제목으로 사용
- 변경 내용·이유, 검증 방법·결과, 리뷰 요청 사항 기록
- 대화 맥락을 모르는 팀원도 변경 전후와 이유를 이해할 수 있게 작성

### 검증

- 기존 build·test·lint 중 변경에 필요한 검사 실행
- 문서는 내용·링크·예시 확인, UI는 필요한 화면 첨부
- **미검증 부분**은 이유 명시
- 체크리스트는 작성자가 실제 확인 후 표시
- 미검증이면 검증 체크를 비워두고 merge 여부를 상대방과 판단

### Issue 연결

- 전체 완료: **`Closes #3`** — 기본 브랜치에 merge 시 Issue 자동 종료
- 일부 진행·관련 작업: **`Refs #3`** — 참조만 연결
- 관련 Issue가 없으면 해당 항목 삭제

## 5. 리뷰·Merge·정리

### 리뷰

- 상대방은 목표대로 동작하는지, 오류 가능성, 코드 이해도, 검증 충분 여부 확인
- **필수 수정**과 선택 제안 구분
- 작성자는 피드백 반영 또는 미반영 이유 설명
- 승인 후 변경이 생기면 재리뷰 요청

### Merge

- Draft 해제, 상대방 승인·필수 검사·리뷰 의견 처리 확인
- 위 조건 충족 후 작성자가 **Squash merge**
- 상대방 부재 시 리뷰 대기
- 최종 commit 제목은 `PR 제목 (#PR 번호)` 사용
- 본문(Extended description)은 선택. 추가 설명이 필요하면 변경 이유·핵심 변경을 1~3줄로 작성하고, 제목만으로 충분하면 생략
- 자동 입력된 중간 commit 목록은 정리. PR 본문 전체 복사 불필요

### 정리

- 원격 작업 브랜치는 자동 삭제 설정
- 로컬 작업 브랜치는 PR merge를 확인하고, 미커밋·미전송·미반영 변경이 없을 때 삭제
- merge한 브랜치 **재사용 금지**
- 후속 작업은 최신 `main`에서 새 브랜치 생성
